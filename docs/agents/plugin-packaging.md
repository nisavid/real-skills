# Build and verify the native repository package

Each package root supplies the promoted engineering and productivity skills to Claude Code and Codex from their original directories. The shared `real-skills` marketplace catalogs select a separate reviewed source in `nisavid/real-skills` for each of `real-skills-leashed` and `real-skills-unleashed`. Each ref is a full lowercase 40-character commit ID or a fully qualified release tag shaped as `refs/tags/vM.m.P+from.M.m.U`, with decimal components that have no leading zeroes. Both catalogs must use the identical ref string for each edition, and the two editions must have distinct refs. Moving branch refs and abbreviated or ambiguous selectors stop generation. Standalone catalogs select `./` for the package built from that checkout. The native manifests expose only the promoted set.

For portable agent-plugins and Claude release ZIPs, use [the release archive procedure](release-archives.md).

## Inputs and ownership

Use this procedure when generating the Codex manifest after an authorized metadata or packaging change, checking package drift, changing marketplace routing, or preparing a consumer of the packaged skills. Ordinary skill use and unrelated documentation edits do not require generation.

The maintained sources are `skills/engineering/`, `skills/productivity/`, `.claude-plugin/plugin.json`, and `LICENSE`. Preserve upstream skill bytes, attribution, executable bits, and invocation settings. The Claude source manifest lists every promoted skill directory exactly once. Each selected directory must contain `SKILL.md` and `agents/openai.yaml`. Duplicate skill names, paths outside the promoted buckets, symlinks in selected trees, nested `SKILL.md` files, and identity or version disagreement with `package.json` stop generation.

`scripts/build-plugin-package.mjs` generates only `.codex-plugin/plugin.json` from the Claude source manifest. Both native manifests select the same original directories. The Codex display name follows the package identity. `real-skills-leashed` displays as Real Skills [Leashed] and `real-skills-unleashed` displays as Real Skills [Unleashed]. Ivan D Vasin is named as the fork developer and Matt Pocock is credited as the original author. The builder leaves the Claude source manifest, license, skill trees, and other repository contents intact. The root uses native compatibility manifests; a root `plugin.json` would select a different Codex discovery mode and is rejected by the package check.

Use Node.js 22 or newer. The build and unit tests use Node's built-in modules and require no dependency installation. The compatibility regression also requires a Codex executable with the app-server `plugin/read` route. Read [the native Codex compatibility reference](codex-plugin-compatibility.md) when changing manifests, marketplace routing, or compatibility checks.

## Procedure

1. Record the candidate revision with `git rev-parse HEAD` and inspect `git status --short`. Confirm authorization for the intended source or packaging change and preserve unrelated work. A downstream consumer loads this procedure at its reviewed revision and verifies that the relevant source and package changes have a clean review before dependent execution. During producer self-use, record the candidate revision and rerun the checks below before review.
2. Run `npm run build-plugin-package` when the source manifest changes. Generation validates the promoted inventory and both catalog routes before updating only the native Codex manifest. A recoverable write or replacement failure leaves an existing manifest unchanged; temporary files are removed when cleanup succeeds. This does not cover concurrent writers or power loss. If validation fails, resolve the source or routing decision within the task's authority before retrying. Skill content changes need no copies to refresh; both harnesses read the original directories.
   The Leashed native manifests use `./assets/wayfinder.svg`. The supplied source artwork is `assets/wayfinder-source.svg`. Run `python3 scripts/build-wayfinder-icon.py --check` to verify the deterministic, style-free derivative. If it is stale, regenerate it with `python3 scripts/build-wayfinder-icon.py` and review the resulting asset. Claude's directory checker rejects the source SVG's style element. The [distinct Unleashed icon](https://github.com/nisavid/real-skills/issues/79) has its own qualification.
3. Run `npm test`, `npm run check-plugin-version`, and `npm run check-plugin-package`. Check mode performs no writes. It rejects a missing or stale Codex manifest, an invalid promoted inventory, or catalog routing that disagrees with the package or the shared variant sources. Rebuild a stale derived manifest, then rerun verification. Compare authorized skill changes against the upstream revision separately; package checks establish selection and generated metadata consistency, not upstream provenance.
4. After manifest or marketplace changes, run `claude plugin validate . --strict` and `claude plugin validate .claude-plugin/marketplace.json --strict`. Validate the root package and the marketplace separately. The accepted plugin-validation warning is that root `CLAUDE.md` is not loaded as plugin project context: this file supplies repository guidance, while the manifests supply plugin skills. If strict root validation fails only for that warning, also run `claude plugin validate .` and require success with exactly that plugin-validation warning. Claude 2.1.316 separately reports `ICON_MISSING` as a plugin-directory advisory and states that its directory checks do not change the plugin-validation result. For PR #19 and the planned GitHub and native releases, retain that advisory for directory submission without treating it as an additional plugin-validation warning. Marketplace strict validation must pass. Retain both root results, the marketplace result, and all warning text; every other warning or error remains a gate. Directory submission retains its separate requirements and hold.
5. Before publication or dependent use, run `npm run test-codex-plugin` against the candidate and require success. It uses `codex` by default; set `CODEX_BIN` to the intended direct executable when selecting another installation. The test starts isolated app-server processes and exercises real discovery with the repository package and controlled fixtures. It checks exact promoted selection, non-promoted exclusion, native recursion, optional long description, and the portable format boundary. Retain the test output, including the reported Codex version. Consumers run this command with their own Codex executable on the reviewed package revision before dependent execution. Source evidence, unit tests, and an earlier executable's passing result do not replace this check. An unavailable executable or failed regression blocks that publication or use.
6. Before publication or dependent use, inspect the diff and verify the two catalogs agree on routing, both native manifests select the same promoted directories, and invocation metadata remains paired between `SKILL.md` and `agents/openai.yaml`. For the shared marketplace, select each edition pin only after its source review is clean. Resolve it to a commit and verify that commit's package identity, promoted inventory, invocation metadata, and required source evidence. Record the catalog ref, resolved commit, and reviewed source revision together. A tag name is mutable: a fully qualified tag removes branch/tag ambiguity but does not guarantee that the tag will not move. Recheck the recorded resolution before dependent use and stop on drift. The builder validates syntax, distinct known editions, the exact source URL/object shape, and cross-catalog agreement; it neither contacts the remote nor establishes review status, tag immutability, target content, or client acceptance. Qualify each selected ref and its install and update behavior in each client. The intended `main`/`vanilla-plus` source split and any later `stable`/`stable-vanilla-plus` channels retain their separate transition and qualification work; this mechanism does not move those refs. Complete the repository's independent review on the final revision, then follow `checkpointing-and-publishing-git-work` for publication. Consumers record that reviewed revision and run check mode on the same inputs before relying on the package.
7. For a candidate with a plugin icon, inspect its packaged artwork against light and dark backgrounds before publication. Record the candidate revision, package and surface or preview method, and the legibility result for each background. Inspect each selected provider surface when that observation is authorized and available; otherwise record provider rendering as unobserved. A local preview does not establish how a provider renders the icon. An illegible icon blocks the affected candidate until corrected.

The version workflow generates the Codex manifest after synchronizing the Claude source manifest version. CI rejects stale generated metadata and runs the Codex regression against `0.160.1` and the current `latest` package. Record the actual tested version from each run; this matrix does not establish a continuous supported version range.

## Completion evidence

Retain the reviewed revision, passing command results with the actual Codex version, the source-preservation comparison, validation of each changed catalog or native manifest, and the icon appearance record when applicable. Harness discovery requires separate evidence on the repository-root candidate: compare each harness's observed skill names with the promoted source manifest and confirm non-promoted names are absent. Preserve the source invocation metadata and report whether runtime enforcement was observed. Catalog parsing and session discovery establish neither marketplace installation nor workflow execution. Installation or host configuration changes need their own task authorization.

Capture useful corrections in this maintained procedure and rerun the affected checks and independent review. Publication, consumer acceptance, and changes to upstream skill behavior keep their existing owners.
